# Contributing

Thanks for looking. Read this first, because what we accept is narrower than most
repositories.

## What we accept

- Bug reports with a reproduction.
- Fixes for bugs that already have an accepted issue.
- Documentation corrections, including small ones.
- Evaluation results that contradict something we published, with your method attached.

## What we usually decline

- Large refactors and dependency bumps that nobody asked for.
- New features arriving as a finished pull request with no prior issue.
- Style-only changes. Formatting is enforced by tooling, not by review.

Open an issue before writing anything substantial. A rejected pull request wastes your time
more than ours, and the honest reason for most rejections is that the change did not fit a
roadmap we had not published.

## Process

1. Open an issue and wait for a maintainer to agree on the approach.
2. Fork, branch from `main`, and keep the change focused on one thing.
3. Write a test that fails before your change and passes after it.
4. Run the repository's lint and test commands. Check its own README for what those are.
5. Open a pull request that references the issue and describes what you verified.

Commit messages: imperative mood, first line under 72 characters, no trailing full stop.
We do not require a specific commit convention beyond that.

## Review

One maintainer approval merges. We aim to give a first response within **5 business days**.
Reviews go to the code, never the person. If a review reads as brusque, assume time
pressure rather than hostility, and say so if you would like more detail.

## Research claims

If your contribution asserts a capability or a result, it carries a number or a citation.
That standard applies to our own work as well.

## Licence

Contributions are licensed under the repository's own licence. Check the `LICENSE` file, as
it varies between repositories. By opening a pull request you confirm you have the right to
submit the code under that licence.
